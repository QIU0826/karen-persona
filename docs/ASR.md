# 语音识别（ASR，v0.9.0）

> 目标：**她能听懂你发的语音**。此前用户发来的 QQ 语音条一直只是 `[语音]` 占位——
> 她只能发语音、不能收语音，这是"像真人"最后一个明显短板。

## 1. 方案：本机 faster-whisper（CPU int8）

| 方案 | 结论 |
|---|---|
| 云端 ASR API | 未采用：隐私优先 + 额外费用 |
| macOS Speech 框架 | 不可从 Node/Python 简单调用，且需要系统授��� |
| **faster-whisper（采用）** | CTranslate2 后端，CPU int8，`small` 模型中文可接受；M 系列单条 1–3s 语音约 **0.9–1.5s** |
| whisper.cpp | 需要编译 + ggml 模型；效果相近，但依赖链更多 |

模型：`Systran/faster-whisper-small`（~484MB），中文输出经 **OpenCC t2s** 统一转简体
（whisper 常输出繁体「天氣／吃飯」）。

## 2. 目录与清理

| 内容 | 位置 | 清理 |
|---|---|---|
| Python 环境 | `services/asr/.venv/`（约 250MB） | 删目录 |
| 模型权重 | `services/asr/models/faster-whisper-small/`（465MB） | 删目录 |
| 运行数据 | 无（不落盘音频；仅内存处理） | — |

## 3. 启动与开关

```bash
npm run asr:start     # 启动服务（默认 127.0.0.1:18085）

# .env
KAREN_ASR=on
KAREN_ASR_URL=http://127.0.0.1:18085
```

服务没起/超时/解码失败 → **静默回退 `[语音]` 占位**，聊天不受影响（和生图一致）。

## 4. 链路

```
QQ 语音条(SILK) → 桥接下载(url) → silk-wasm decode → PCM16
  → 包 WAV 头 → POST /transcribe（本地 faster-whisper）
  → 简体文本 → 注入对话（[语音：...]）
```

隐私：日志只记字符数与耗时，**不打印识别正文**。

## 5. 模型下载（本机可复现，和生图同一套问题）

HF 直连不通、hf_hub 默认走 Xet CDN 也不可达；`hf-mirror.com` 可用但单连接限速。
做法：

1. 小文件（config/tokenizer/vocabulary）直接 `curl` 镜像 resolve；
2. `model.bin`（484MB）用 **64MB/块、4 路并发 curl** 下载后按序拼接（约 2–4MB/s）。

## 6. 实测（v0.9.0）

| 场景 | 耗时 | 结果 |
|---|---|---|
| 文本→TTS SILK→ASR（约 4s 语音） | 1414ms | 「今天天气不错,我们晚上一起去吃饭吧。」 |
| 纯 WAV（say 生成，1.6s） | 962ms | 「明天下午3点开会。」 |
| 垃圾字节 / 不支持格式 | — | 明确失败并回退，不抛异常 |
| 桥接 E2E（假 ASR 服务） | — | 转写文本真的进入模型 prompt ✅ |

## 7. 真实长跑验证（v0.9.2）

验证台新增 `voice` 场景 + `--voice-in`：用 TTS 合成 SILK，经本地 HTTP 服务下发给 bridge
（模拟 NapCat 的语音条 url），走**真实 ASR 服务**跑 4 轮。

实测（2026-10-21，报告 [VOICE_ASR_E2E.md](VOICE_ASR_E2E.md)）：

| 指标 | 结果 |
|---|---|
| 入站语音 / ASR 成功 | **2 条 / 2 次** |
| 记忆探针（语音说「下周三去上海签星潮合同」，文字回问） | **1/1 通过**，她答「上海呀 星潮的合同 三天」 |
| 回复延迟 p50 / p95 | 4.3s / 6.1s（含 ASR） |
| 成本 | ¥0.0217（bridge ¥0.0155 + 评审 ¥0.0031） |
| LLM 评审 | 连贯 4/5、记忆 4/5、真人感 4/5、主动 3/5 |

结论：**「语音 → 转写 → 事实抽取 → 记忆召回」整条产品闭环成立**（不是只有"接口通了"）。

## 8. 鲁棒性压测（v0.9.3，`npm run asr:robustness`）

用 10 句聊天语料 × 8 组条件（标准/慢/快语速、台湾腔、粤语口音、10dB/5dB 加噪）测**字错率 CER**：

| 条件 | CER | 延迟 |
|---|---|---|
| Tingting 标准语速（基线） | **3.0%** | 1051ms |
| Tingting 慢速 140 | 3.0% | 1070ms |
| Tingting 快速 240 | 3.0% | 1085ms |
| Meijia（台湾腔） | 3.0% | 1085ms |
| Sinji（粤语口音） | 9.6% | 1100ms |
| Tingting + 10dB 噪声 | 4.4% | 1106ms |
| Tingting + 5dB 噪声 | **10.7%**（最差） | 1121ms |
| Meijia + 10dB 噪声 | 10.5% | 1149ms |

**结论：`small` 模型在本机场景够用，不需要升级 `medium`**（升级后 CPU 会慢 2–3 倍，而当前
噪声条件下也只有 ~11% 字错，对聊天理解影响有限）。

典型错误是**近音字**（产品→传品、橘猫→之余猫、黏人→年人、上线→上限）——这类错误对语义影响小，
上下文能纠回来。

> 一个诚实的发现：`say -v '?'` 列出了 9 个 zh_CN 音色，但**真正能发声的只有 Tingting**，
> Meijia(台)/Sinji(粤) 是另外两种；其余（Rocko/Grandma/Sandy…）在本机未安装，合成出来是 3KB 静音。
> 所以「男女老少音色多样性」还没测——这也说明**真实人声样本仍然缺**。

## 9. 局限（如实）

- 只有中文（`language="zh"` 固定）；中英混说可能丢英文词；
- `small` 模型对口音/远场/背景噪声会错字，长句可能断句；
- 语音条需要 NapCat 提供可下载 URL；没有 URL 时回退占位；
- CPU 推理，和生图（MPS）不抢同一算力，但同时高负载时会变慢；
- **不做说话人识别**（群里谁的语音分不出来，群聊语音仍不支持）。

## SenseVoice 语音理解（2026-10-22）

- 服务：GPU3 `127.0.0.1:18112`；Mac 隧道 `19112`
- 模型：`iic/SenseVoiceSmall`（ASR + 情绪 + 音频事件）
- 产品开关：`KAREN_ASR_BACKEND=sensevoice`、`SENSEVOICE_URL=http://127.0.0.1:19112`
- 输出示例：`[语音：今天好累啊｜语气：低落｜背景：音乐]`
- 失败自动回退 faster-whisper 纯文字。
- **限制**：情绪标签实测会误判（angry/neutral 有时判 sad）；唱歌、阴阳怪气没有可靠验证，
  不能承诺准确识别；要真正音频语义仍需音频大模型（Qwen-Omni 等）。
