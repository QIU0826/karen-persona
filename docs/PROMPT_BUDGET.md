# Prompt 预算审计（离线实测）

> 目标：回答「每轮对话实际塞给模型多少 prompt、钱和延迟主要花在哪一段、哪些段可以砍」。
> 结论全部来自本机真实数据或真实函数调用；**token 为粗估**（见 §1.3），标注「估算」的数字不要当计费真值使用。
>
> - 审计日期：2026-10-20（北京时间）
> - 基线：仓库 `HEAD = v0.3.3` 的 Prompt 构建代码（`src/persona/prompt-builder.ts`、`src/data/history.ts` 与 HEAD 一致）。审计进行期间工作树有并行未提交改动（v0.4.0 主动消息四链路），本报告 S5 按 v0.3.3 的 `processProactive()` 注入构造；v0.4.0 合入后 S5 的「此刻的冲动」块会多一小段链路说明，重跑脚本即可刷新（§7）。
> - 只读声明：`llm_usage` 用 `better-sqlite3` 以 `readonly:true, fileMustExist:true` 打开，只执行 `SELECT`；全程不写 `data/`、不联网、不调用 LLM、不读 `.env`。
> - 复现脚本：`scripts/prompt-budget.ts`（固定 fixture + 固定种子 RNG，重复运行结果逐字节一致）。

## 0. 结论摘要（TL;DR）

1. **实测输入远大于输出**：81 次真实调用中，prompt_tokens p50 = **2076**、p95 = **2788**、max = **2890**；而 completion_tokens p50 只有 **9**、p95 = 62。成本与延迟主要由输入侧（prompt）决定。
2. **对话轮普遍在 2k+**：仅对话轮（chat + chatStream，51 次）prompt p50 = **2241**；**68.6% 的对话轮 ≥2000 tokens、27.5% ≥2500**；QQ 主路径 chatStream 的 p50 更高，为 **2478**。
3. **缓存已经在兜底**：49.3% 的 prompt token 命中缓存（60032 / 121747），64.2% 的调用有缓存命中；chatStream 单次 cached_tokens 中位 **1024**，与静态块估算 1681 tokens 的 60.9% 相当——静态人设前缀基本落在缓存里。
4. **系统提示词里最大的一段是「重要提示」**：典型轮（S2 关系稳定）系统提示词 **3591 字符 ≈3158 tokens**；单段最高为「重要提示（行为规则）」**835 字符 / 750 tokens / 23.3%**，且同一批约束散落多处（「括号」出现 3 次、「编造」出现 4 次）。
5. **真正的按轮增量在动态注入**：S2 的注入/摘要块合计 **968 字符（27.0%）**，其中用户事实 198、旧消息摘要 176、RAG 153、动态风格参考 130 是主要项；这些内容**不享受静态前缀缓存**，是每轮新增的上下文与费用。
6. **静态块是固定成本**：人设静态块 **1900 字符 ≈1681 tokens**，占 S2 系统提示词 **52.9%**（S1 初识场景占 73.1%）。砍它不一定省钱（缓存命中），但能降低上下文占用与首 token 前的处理量。

## 1. 方法与口径

### 1.1 做了什么

1. **离线构造 5 个典型状态**，真实调用 `buildPrompt()` + `buildChatMessages()`，并调用 orchestrator / `chat.ts` 会追加的上下文块对应的**导出 formatter**（RAG、T1 状态弧、用户事实、动态风格参考、热点、危机提示、反重复、媒体请求提示、时间标签、主动冲动注入），按段落统计字符数；
2. **只读查询** `data/memory.sqlite` 的 `llm_usage` 表，统计真实调用的 prompt_tokens 分位、按用途/天/小时分布、大 prompt 占比、缓存与成本。

不包含：网络请求、真实 LLM 调用、任何写库操作。

### 1.2 五个场景（离线 fixture）

| ID | 场景 | 历史消息 | 运行时状态 | 注入块 |
| --- | --- | --- | --- | --- |
| S1 | 初识低亲密度 | 6 条 | 亲密度 1.5 / 情绪 0.05 / distant | 无 T1/T2、无用户事实 |
| S2 | 关系稳定 | 40 条 | 亲密度 7.2 / 情绪 0.25 / close | 旧消息摘要 + T2 5 条 + 用户事实 10 条 + T1 8 条 + 风格参考 2 条 + 热点 + 纠正层 + 媒体请求 |
| S3 | 有 T1 快照 + T2 记忆 | 24 条 | 亲密度 4.5 / 情绪 -0.1 / neutral | T2 6 条（较长记忆）+ 用户事实 4 条 + T1 8 条 |
| S4 | 危机轮 | 31 条 | 亲密度 6 / 情绪 -0.7 / neutral | 危机安全提示 + T2 3 条 + 用户事实 8 条 + T1 8 条 |
| S5 | 主动消息轮 | 20 条 | 亲密度 7 / 情绪 0.3 / close | 主动冲动注入 + T1 8 条（与 `processProactive` 一致，无 RAG/事实/时间标签） |

fixture 说明：人设为内置 `xiaoya`；会话消息平均约 14 字/条（真实用户通常更长）；旧消息摘要按 `buildChatMessages` 的 10 条 × 40 字截断逻辑生成。

### 1.3 token 估算口径（重要）

- **估算公式**：CJK 字符（汉字 + CJK 标点）≈ **1 token**，其余字符（ASCII/空白/emoji）≈ **0.3 token**。
- 这是**粗估**，不是 tokenizer 真值：用 S2 交叉验证时，估算整轮 3374 tokens 比实测 chatStream p50（2478）**高 36.2%**（§3.5）。因此：
  - 「段落之间谁更大 / 占比」用估算即可；
  - 「每轮多少 token / 多少钱 / 多快」请以 `llm_usage` 实测为准。
- 字符数均为 JS `String.length`（UTF-16 code unit），同一字符串可复现。

### 1.4 分段切分方式

- `buildPrompt()` 的输出按真实段落标记切开（`## 你是谁` / `## 重要提示` / `## 你的原则` …），静态段与动态段（状态标签、行为脚本、L1 规则、关系、纠正层）分开计数；
- orchestrator 的追加块按真实拼接顺序计入（风格参考 → 热点 → 危机 → T1 → 用户事实 → 反重复 → 媒体提示 → 时间标签；主动消息为「冲动注入 → T1 → 反重复」）；
- `buildChatMessages()` 追加的旧消息摘要单独成段；`chat.ts` 在 system 末尾追加的 RAG 单独成段（含前导换行）；
- 脚本内有自检：所有分段拼接必须逐字等于最终 system message，否则直接报错（输出中所有合计都通过该自检）。
- **未纳入**的块（orchestrator 私有常量 / 低概率条件分支，无法离线无副作用调用）：未化解冲突提示、说话动作（talk-moves）提示、叙事弧注入、中断残留提示。它们只在特定轮出现，单项约几十到一两百字符，不影响 TOP 结论。

## 2. `llm_usage` 实测（真实调用记录）

- 样本：**81 次调用**，时间范围 2026-10-20 00:10 → 17:35（北京时间）

| 指标 | 数值 | 说明 |
| --- | --- | --- |

## 6. 局限与未测项

1. **llm_usage 样本小**：81 次、仅 1 个自然日、单机；p95/p99 受小样本影响（p99 = max），不能外推为长期分布；「按天趋势」无法给出。
2. **token 是估算**：CJK≈1 / ASCII≈0.3，实测 S2 估算比 chatStream p50 高 36.2%，只适合做段落相对比较；计费/延迟请以 `llm_usage` 实测为准。
3. **场景是 fixture**：历史消息平均 14 字/条（真实用户更长）、RAG/事实条数为典型值而非系统上限；所以「真实最坏情况」可能更高。
4. **未纳入的注入块**：未化解冲突提示、说话动作提示、叙事弧注入、中断残留提示（orchestrator 私有常量/低概率分支）。单项几十到一两百字符，不影响 TOP 结论，但会使「真实系统提示词」比本报告略长。
5. **基线时点**：本报告对应 HEAD v0.3.3 的 `buildPrompt` / `buildChatMessages` 与 v0.3.3 的主动消息注入；审计期间工作树有 v0.4.0 未提交改动（主动消息四链路，会改 S5 的注入文案）。其余四场景不受影响。
6. **未测**：真实 tokenizer 数值、DeepSeek 缓存价/峰谷价的精确成本、prompt 长度与 TTFT 的定量关系、多用户 owner 隔离对静态缓存 key 的影响（`getStaticCache` 按 persona.name 缓存）。
7. **只读边界**：`llm_usage` 为真实调用元数据，本报告只导出聚合统计，未导出对话正文。
