## 延迟为什么从历史的 2.0s 变成 5.1–5.4s

**不是性能退化，是 v0.6 节奏模拟器的设计结果。** 本机实测（深夜 23:00 后人设）：

- readDelay（看到消息→开始打字）：**1600ms**
- 每字耗时：**395ms**（白天约 293ms）；一条 6–7 字气泡 ≈ 2.4–2.8s
- 一轮 2–3 条气泡累计打字 ≈ 5.3s

也就是说 5.1s 的首条延迟里，绝大部分是"像人一样打字"的时间，不是模型慢（模型首 token 仍是 1–2s）。
**取舍记录**：真人聊天本来就不是秒回；但如果实际体验觉得"太慢"，把 `pacing` 的
readDelay/每字耗时下压即可（`src/bridge/pacing.ts` 常量），不需要动其它逻辑。

## 第二轮之后：多媒体相关性（2/5 → 4/5）

评审原话（第 ① 轮）：「照片/语音频繁但时机生硬，常与当前话题无关（如答'杭州'却发旧照），
配文与图片内容对不上，像硬塞」。

根因两个，都在 `src/impulse/`：
1. 选图只看情绪/时段/亲密度，**不看这轮在聊什么**；
2. 配文是固定池（「随手拍了一张」「喏」），和话题无关。

修法（新增纯函数模块 `src/impulse/media-relevance.ts`，10 条单测）：
- **相关性门控** `assessPhotoRelevance`：只有三种情况发图——他点名要 / 场景命中（且图库里真有这类图）/
  她刚在分享生活（我在…、刚下班、路上…、在煮… 等信号）。其余（抽象话题、纯问句）**宁可不发**。
- **场景配文** `buildSceneCaption`：晚霞→「天这样了」、雨→「雨还没停」、猫→「它又赖着不走」、
  咖啡→「这杯续命」…（10 个场景池），比通用池贴题。

第 ②/③ 轮复验：多媒体 4/5、4/5；评审原话变成「照片配文自然（'喏，就这个''这小家伙又来了'），
语音时机也合理」，只剩「第 6 轮重复发昨天的店里照片略显凑数」这类小问题。

## 第三轮：长程复读（评审新发现 → 已加检测与提示）

第 ② 轮评审抓到：「第 9 轮和第 19 轮回复逐字重复，第 11 轮和第 20 轮也几乎一样」。
但验证台的「复读对」指标是 **0** —— 因为它只跟**相邻**一条比，隔 8 轮的复读永远检测不到。

修法：
- **生产检测窗口 3 → 10**（`DEFAULT_LONG_RANGE_REPLY_COUNT`）：`detectRepetition` 现在能抓到隔多轮的原样复读；
  开头词统计仍只用最近 3 条（否则语气词会误判）。
- **静态提示规则**（不引用原文，避免 v0.3.3 那次的"回放整句→照抄"）：
  「同一个问题他再问一遍（隔了几轮也算），不要复述你上次的答案：换个说法，补一个上次没提的细节」。
- **验证台新增指标**「复读对（长程，10 轮窗口）」。

第 ③ 轮复验：长程复读对 **2**（真实存在过、现在可观测），评审不再提「逐字重复」。

## 一个需要说明的"低分"：记忆 3/5 来自「怎么认识」含糊

三轮里她都答「记不太清了，你提醒我一下」——评审把它当"回避"扣分，**但这其实是守卫的正确行为**：
人设没有相识背景、用户也没说过 → 她不该编。
真正该做的是让用户能提供这个背景：`npm run setup` 已经会问「你们怎么认识的」并写进
`config.relationship_background`（有依据时守卫完全不干预），只是这次验证台用的是空配置。
**结论：这不是 bug，是"默认人设没有相识设定"的必然结果**；下一版可以让 setup 更显眼地提示这项。
